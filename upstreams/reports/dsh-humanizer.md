## 2. Purpose and functionality

The project is a **writing skill plugin for DeepSeek Harness (`dsh`)** built around the slogan "not
'write like a human', but 'write like me'" (`README.md:3`). It has two independent layers:

1. **De-AI detection + rewrite briefing.** `analyzeText` scores a draft 0–100 for "AI-ness" and lists
   matched patterns (`src/core/analyze.ts:23-53`). `buildRewriteBrief` turns that into a natural-language
   instruction block for the calling agent to apply itself (`src/core/render.ts:113-155`).
2. **Personal voice clone.** `extractFingerprint` derives a deterministic style fingerprint from the
   user's own samples (`src/core/fingerprint.ts:122-212`), persists it as a named Voice Profile
   (`src/store.ts:76-82`), scores new text against it (`src/core/score.ts:50-98`), and emits a
   voice-matched rewrite brief (`src/voice.ts:154-192`).

Explicit non-goal, stated three times: **the plugin performs no LLM calls.** "This is a **skill for the
agent**, not an LLM wrapper: it performs no model calls. It only produces rules, fingerprints, scores,
and rewrite briefs — the agent does the actual rewriting itself." (`README.md:5`); echoed at
`src/core/render.ts:2-4` ("The plugins never call the LLM themselves: they hand the agent a brief, and
the agent performs the rewrite in its own turn.") and `README.md:89` ("**No LLM calls**").

Declared design decisions (`README.md:87-91`): no LLM calls; single self-contained bundle with no
unpublished shared dependency; file-based persistence under `~/.dsh/*.json` requiring no storage backend.

Category → human label map (`src/core/rules.ts:27-35`): `empty-opener` → "Empty opener"; `cliche` →
"AI cliché"; `hedge` → "Hedging / qualifying"; `transition` → "Template transition"; `summary-ending`
→ "Summary-style ending"; `mechanical-parallel` → "Mechanical parallelism"; `over-explain` →
"Over-explaining".

Severity semantics: `1 = mild tell, 3 = strong tell` (`src/core/rules.ts:7`, restated in
`renderRules` at `src/core/render.ts:37`). Severity is **not** used as a normalised weight anywhere —
it enters only the raw `aiScore` sum (`src/core/analyze.ts:34`) and the detection sort
(`src/core/rules.ts:356`).

Detection aggregation semantics (`detectIssues`, `src/core/rules.ts:333-357`): for each rule it
iterates every pattern, counts `text.match(re)` hit counts into a single `count`, keeps **the first
matched phrase** as `phrase` (`:343`), and only emits a `Detection` if `count > 0` (`:346`). Results are
sorted descending by `severity * count` (`:356`). Because `count` is totalled per rule, `phrase` is not
necessarily the most frequent match — it is the first match of the first pattern that fired.

False-positive surface: several patterns are bare English words that occur legitimately in human prose —
`seamless`, `robust`, `leverage`, `scalable`, `streamline`, `foster`, `unlock`, `holistic`,
`somewhat`, `potentially`, `essentially`, `basically`, `there`, `foster`, plus CJK single-concept terms
such as `心智`, `红利`, `赛道`, `天花板` whose presence alone is weak evidence (`src/core/rules.ts:109-133`,
`:149`, `:157`). The detector has no co-occurrence requirement, no density threshold, and no
document-length gate, so a single incidental use of `robust` emits a `severity: 2` detection worth 2
`aiScore` points.

**Overlapping patterns (verified by execution at inventory time):** two literal phrases are claimed by
two different rules each — `换句话说，` in `over-explain-zh` (`rules.ts:309`) and as `^换句话说` in
`transition-zh` (`rules.ts:236`); `值得注意的是` in `hedge-zh` (`rules.ts:203`) and as `^值得注意的是，`
in `transition-zh` (`rules.ts:236`). Because the `transition-zh` copies are `^`-anchored and no `m` flag
is set (`rules.ts:319`), **those two overlap only when the phrase sits at absolute position 0 of the
input** (verified: `new RegExp('^换句话说','gi').test('X。换句话说，')` → false; the unanchored
`over-explain-zh`/`hedge-zh` copies match anywhere). So the double-count is a real but narrow edge case
confined to text that opens with the phrase, not a general inflation of `aiScore`. The broader
consequence of the missing `m` flag is the opposite one: the **37** `^`-anchored patterns in
`transition-en`, `transition-zh`, `summary-ending-en`, and `summary-ending-zh` are **inert everywhere
except position 0** (verified: `'a.\nFurthermore, b.'` does not match `^furthermore,` with flags `gi`,
but does with `gim`).

### Pipeline of `analyzeText`

1. `splitSentences(text)` → sentence array (`analyze.ts:24`).
2. Per-sentence `wordCount`, summed to `words`; `avgSentenceLength = words / sentences.length`
   (`analyze.ts:25-27`).
3. `burstiness = stddev(lengths)` (`analyze.ts:28`).
4. `issues = detectIssues(text)` — note it re-scans the **whole original text**, not the sentences
   (`analyze.ts:30`).
5. Score accumulation, then clamp (see §6).
6. Return, rounding `avgSentenceLength` and `burstiness` to 1 decimal (`analyze.ts:48-49`), and
   `issueCount` = sum of all `issue.count` (`analyze.ts:51`).

`groupIssues` maps category → summed count and returns `label: category` — i.e. **the machine category
string is used as the label**, not the human label from `RULE_CATEGORY_LABELS` (`analyze.ts:66-70`).
This is inconsistent with `renderReport`, which does use `RULE_CATEGORY_LABELS` (`render.ts:24`).
`groupIssues` is exported but **not called anywhere** in `src/` — none found.

### Text segmentation and tokenization (`src/core/text.ts`)

- `CJK_RE = /[\u3400-\u9fff]/g` (`text.ts:6`) — CJK Unified Ideographs Extension A + the main URO
  block. It does **not** cover Hiragana/Katakana, Hangul, or CJK Extension B+ (surrogates).
- `LATIN_WORD_RE = /[A-Za-z0-9]+(?:['’-][A-Za-z0-9]+)*/g` (`text.ts:8`) — alphanumerics with internal
  ASCII apostrophe, U+2019 right single quote, or hyphen.
- `detectLanguage(text)`: counts CJK chars vs `[A-Za-z]`; `total === 0 → 'en'`; `cjk === 0 → 'en'`;
  `latin === 0 → 'zh'`; otherwise `cjk / total > 0.6 ? 'zh' : 'mixed'` (`text.ts:13-21`). Threshold
  **0.6** is the exact cut. Empty string returns `'en'` (asserted in `test/text.test.ts:38`).
- `wordCount(text) = (#CJK chars) + (#Latin words)` (`text.ts:24-28`). "Count one CJK character as one
  token and one Latin word as one token." So `'hello 世界'` = 3 (`test/text.test.ts:32`).
- `splitSentences(text)` (`text.ts:35-60`), 5-stage normalisation:
  1. Protect honorific/abbreviation dots by replacing `.` with U+0000 for
     `\b((?:dr|mr|mrs|ms|prof|sr|jr|st|vs|etc|no)\.)(?=\s+[A-Z])` (`text.ts:38-40`).
  2. Protect `e.g.` / `i.e.` before whitespace (`text.ts:42`).
  3. CJK full-width stops always end a sentence: `([。！？]+)(["'”’」』）\)\]]*)` → newline
     (`text.ts:46`).
  4. ASCII `!?` end a sentence before whitespace/end or a closing quote (`text.ts:48`).
  5. ASCII `.` ends a sentence before whitespace/end, **only when followed by whitespace or end**, which
     is what leaves `3.14` intact (`text.ts:50`).
  6. `…+` is a boundary (`text.ts:52`).
  7. U+0000 restored to `.` (`text.ts:54`).
  Then split on `\n+`, trim, drop empties (`text.ts:56-59`).
- `stddev` is the **population** standard deviation (divide by `n`, not `n-1`) (`text.ts:63-68`).
- `median` averages the two middle values for even lengths (`text.ts:70-75`).
- `tokenize(text)` (`text.ts:78-91`): Latin words of length ≥ 2, lowercased, **plus** CJK bigrams
  produced by first reducing the text to a CJK-only skeleton
  (`text.match(/[\u3400-\u9fff]+/g) ?? []).join('')`) and then sliding a 2-char window. Consequence:
  the skeleton joins across punctuation and sentence boundaries, so bigrams can straddle
  punctuation/paragraph breaks. No word segmentation dictionary, no jieba, no ICU.
- `EN_STOPWORDS` is a 49-entry English-only `Set` (`text.ts:93-99`); `isStopword(token)` is a plain set

## 6. Scoring — quote the actual code

There are **two entirely separate scores**, not one blended score.

### 6a. `aiScore` — AI-ness of a draft (single scalar 0–100)

Exact code (`src/core/analyze.ts:32-41`):

```ts
  let aiScore = 0
  for (const issue of issues) {
    aiScore += issue.severity * Math.min(issue.count, 5) * 2
  }
  // Uniform rhythm is a classic tell: few very short / very long sentences.
  if (sentences.length > 4 && burstiness < 1.5) aiScore += 10
  // Run-on averages read machine-generated.
  if (sentences.length > 3 && avgSentenceLength > 32) aiScore += 5
  // No issues at all and varied rhythm → genuinely low.
  aiScore = Math.max(0, Math.min(100, Math.round(aiScore)))
```

- Range: `0–100`, clamped and rounded, **higher = more AI-like** (`analyze.ts:10`, rendered as
  `AI score: ${report.aiScore}/100 (higher = more AI-like)` at `render.ts:13`).
- No weights table. The implicit maximum contribution per rule is `severity * 5 * 2`:
  severity 1 → 10, severity 2 → 20, severity 3 → 30, because `count` is capped at 5 by `Math.min`.
- Two heuristic bonuses: **+10** for uniform rhythm (`> 4` sentences AND `burstiness < 1.5`), **+5**
  for run-on averages (`> 3` sentences AND `avgSentenceLength > 32`).
- Maximum possible is 13 × 30 + 15 = **405 before clamping**, so the 100 ceiling is reachable by a
  short text carrying ~4 severity-3 rules. The score is saturating, not calibrated.
- Not normalised by text length: a long document and a one-sentence snippet with the same raw hit
  counts score identically.

### 6b. `scoreSimilarity` — voice similarity (single blended scalar 0–100 **plus** a per-feature breakdown)

Exact code (`src/core/score.ts:20-25`, `:50-97`):

```ts
function close(a: number, b: number, tolerance: number): number {
  const diff = Math.abs(a - b)
  if (diff <= tolerance) return 1
  // Linear decay: 1.0 at tolerance, 0.0 at 4x tolerance.
  return Math.max(0, 1 - (diff - tolerance) / (3 * tolerance))
}
```

```ts
export function scoreSimilarity(draft: StyleFingerprint, profile: StyleFingerprint): SimilarityResult {
  const p = profile.sentence
  const d = draft.sentence

  const features: ScoreFeature[] = [
    {
      feature: 'sentence-length',
      similarity: close(d.avgLength, p.avgLength, 2),
      weight: 0.2,
    },
    {
      feature: 'rhythm-burstiness',
      similarity: close(d.burstiness, p.burstiness, 1.5),
      weight: 0.2,
    },
    {
      feature: 'punctuation-habits',
      similarity: cosine(draft.punctuation as unknown as Record<string, number>, profile.punctuation as unknown as Record<string, number>),
      weight: 0.15,
    },
    {
      feature: 'stance',
      similarity:
        (close(draft.stance.firstPersonRate, profile.stance.firstPersonRate, 1) +
          close(draft.stance.hedgeRate, profile.stance.hedgeRate, 0.5) +
          close(draft.stance.adverbRate, profile.stance.adverbRate, 0.5) +
          close(draft.stance.contractionRate, profile.stance.contractionRate, 0.5)) /
        4,
      weight: 0.15,
    },
    {
      feature: 'vocabulary-overlap',
      similarity: topOverlap(draft.vocabulary.topWords, profile.vocabulary.topWords),
      weight: 0.15,
    },
    {
      feature: 'sentence-length-spread',
      similarity:
        (close(d.shortRate, p.shortRate, 0.1) + close(d.longRate, p.longRate, 0.05)) / 2,
      weight: 0.15,
    },
  ]

  const score = Math.round(features.reduce((a, f) => a + f.similarity * f.weight, 0) * 100)
  return {
    score: Math.max(0, Math.min(100, score)),
    features: features.map((f) => ({ ...f, similarity: Math.round(f.similarity * 1000) / 1000 })),
  }
}
```

Supporting helpers, verbatim (`src/core/score.ts:27-48`):

```ts
function cosine(a: Record<string, number>, b: Record<string, number>): number {
  const keys = new Set([...Object.keys(a), ...Object.keys(b)])
  let dot = 0
  let na = 0
  let nb = 0
  for (const k of keys) {
    const va = a[k] ?? 0
    const vb = b[k] ?? 0
    dot += va * vb
    na += va * va
    nb += vb * vb
  }
  if (na === 0 || nb === 0) return na === nb ? 1 : 0
  return dot / (Math.sqrt(na) * Math.sqrt(nb))
}

function topOverlap(a: { token: string }[], b: { token: string }[]): number {
  if (!a.length || !b.length) return 0
  const setB = new Set(b.map((t) => t.token))
  const hit = a.filter((t) => setB.has(t.token)).length
  return hit / Math.min(a.length, b.length)
}
```

Exact weight table (sums to `1.0`, asserted by `test/score.test.ts:30-31`):

| `feature` string (exact) | weight | tolerance(s) | similarity source |
|---|---|---|---|
| `sentence-length` | 0.2 | 2 | `close(d.avgLength, p.avgLength, 2)` |
| `rhythm-burstiness` | 0.2 | 1.5 | `close(d.burstiness, p.burstiness, 1.5)` |
| `punctuation-habits` | 0.15 | — | `cosine` over the 7-field `punctuation` object |
| `stance` | 0.15 | 1 / 0.5 / 0.5 / 0.5 | unweighted mean of 4 `close()` calls |

Decay semantics: similarity is exactly `1` within `tolerance`, then decays linearly to `0` at
`4 × tolerance`; beyond that it clamps at `0` (`score.ts:22-24`).

**Answer to "single blended or multi-dimensional": both `aiScore` and `scoreSimilarity().score` are
single blended scalars (0–100), but `scoreSimilarity` additionally returns a per-feature breakdown
array (`ScoreFeature[]`) that is surfaced to the user** (`voice.ts:218-223`: `Voice similarity:
${value.score}/100` then one line per feature as `${f.feature}: ${Math.round(f.similarity * 100)}%
(weight ${f.weight})`). There is no multi-axis vector score.

**Feature coverage gaps in scoring (computed but never scored):** `punctuation` is fed wholesale into
`cosine`, so all 7 punctuation fields count. But **`secondPersonRate`, `transitionRate`,
`aiPhraseHits`, `vocabulary.typeTokenRatio`, `vocabulary.topOpeners`, `platforms`, `sampleCount`,
`totalWords`, `sentence.medianLength`, and `language` are never referenced by `scoreSimilarity`** —
confirmed by reading the whole function (`score.ts:50-97`). Ten of the 25 fingerprint fields are
unused for scoring; `medianLength`, `topOpeners`, `typeTokenRatio`, `aiPhraseHits`, `transitionRate`
and `secondPersonRate` are display-only.

### 7b. How a fingerprint is computed (`extractFingerprint`, `src/core/fingerprint.ts:122-212`)

1. Drop samples whose `text.trim()` is empty; join the rest with `'\n\n'` into one `corpus`
   (`:123-124`). All statistics are computed over the **concatenated corpus**, not per-sample — so
   `sampleCount` records the input count but the features are corpus-level.
2. `splitSentences(corpus)`; `lengths = sentences.map(wordCount)`; `totalWords = sum(lengths)`
   (`:126-128`).
3. `avgLength = totalWords / sentences.length` (0 if no sentences) (`:129`).
4. `shortRate` = fraction of sentences with `wordCount < 8`; `longRate` = fraction with
   `wordCount > 28`. Thresholds are **hard-coded 8 and 28** (`:131-132`).
5. `burstiness = stddev(lengths)` (population σ) (`:183`).
6. Punctuation raw counts over the corpus, then converted with `perHundred` (`:135-141`, `:188-194`).
   Note `:` counts **both** ASCII `:` and full-width `：`; `parentheses` counts `(` `)` `（` `）`;
   `emDash` counts `—`, `--`, and `–` (`:135`); `ellipsis` counts `…` and `...` (`:136`).
7. `perHundred(count, tokens) = tokens === 0 ? 0 : Math.round((count / tokens) * 10000) / 100`
   (`:81-84`) — i.e. "per 100 tokens", rounded to 2 decimals. **So `punctuation.*` and all `*Rate`
   fields are per-100-token densities, not fractions.** This matters when comparing fingerprints: they
   are length-normalised, and can exceed 100 for very dense punctuation.
8. Pronoun stance: `firstPersonEn = /\b(I|me|my|we|our)\b/gi`; `firstPersonZh = /我|我们|咱/g`;
   `secondPersonEn = /\b(you|your)\b/gi`; `secondPersonZh = /你|你们|您/g`. Counts are **summed
   across languages** and divided by `totalWords` (`:143-149`). The Chinese pronoun regexes are written
   without the `i` flag, and the alternation is ordered as shown above.
   **NOTE (verified correction, see §16 item 5):** the Chinese alternation is written `我|我们|咱`, and
   because JavaScript regex alternation is leftmost-first, `我` wins at the position where `我们`
   begins — so `我们` contributes exactly one hit to the count (not two), and the `我们` alternative is
   effectively unreachable. Net effect: `我们` is counted once, `我` alone is counted once, but the
   *distinct concept* of first-person plural is never distinguished from first-person singular, so
   `firstPersonRate` cannot tell an "I" writer from a "we" writer (`:145`).
9. Hedge/transition/AI-phrase rates are derived by **reusing the rule engine**: `detectIssues(corpus)`,
   then sum `count` where `category === 'hedge'` (`hedgeRate`), where `category === 'transition'`
   (`transitionRate`), and `aiPhraseHits` = **all** detections summed regardless of category
   (`:151-160`). So the fingerprint's stance features depend on the rule catalogue.
10. `adverbRate`: English `/\b\w+ly\b/gi` **plus** every Chinese `然` character (`:163-165`).
11. `contractionRate`: `/\b\w+'(?:s|t|re|ve|ll|d|m)\b/gi` — ASCII apostrophe only; U+2019
    contractions (`don’t`) are **not** counted (`:166`).
12. `vocabularyStats` (`:87-104`): tokenize → drop stopwords → drop pure-digit tokens
    (`/^\d+$/`) → frequency map → `topWords` = top 12. `typeTokenRatio` =
    `unique / tokens.length` rounded to 3 decimals, where `unique` is the **non-stopword,
    non-numeric** distinct count but the denominator is the **full** token count (`:101`).
    So TTR is not a standard TTR and is not comparable across languages: CJK bigram token counts
    inflate the denominator.
13. `openerStats` (`:107-120`): for each sentence take `s.split(/\s+/)[0]`, strip leading
    `^["'“”‘’([{\[\]})>]+` and trailing `[，,。.!！?？:：;；]+`; skip if empty or `length < 2`;
    lowercase; top 8. **For Chinese text with no spaces the "first token" is the entire sentence**, so
    `topOpeners` is effectively meaningless for unspaced Chinese — no CJK-aware opener extraction exists.
14. `platforms`: `s.platform?.trim() || 'default'`, counted per **non-empty sample** (`:170-174`).
15. Every `sentence` field is rounded: lengths 1 decimal, rates 3 decimals (`:181-185`).

### 7c. How a fingerprint is stored

Wrapped in a `VoiceProfile` and written by `ProfileStore` (see §9). Excerpts are truncated to
**500 characters each** and capped at `config.maxExcerpts` (default 3, max 10):
`sampleExcerpts: samples.slice(0, config.maxExcerpts).map((s) => s.text.slice(0, 500))`
(`src/voice.ts:70`). `createdAt` is preserved on re-import of an existing id, `updatedAt` is refreshed
(`src/voice.ts:65-66`).

### 7d. How a fingerprint is compared / scored against new text

`voice_score` → `extractFingerprint([{ text: args.text }])` builds a **one-sample draft fingerprint**,
then `scoreSimilarity(draft, profile.fingerprint)` (`src/voice.ts:147-149`). The comparison contract is
therefore **fingerprint-to-fingerprint**, never raw-text-to-text. Only the 6 weighted features in §6b
participate. `README.md:59` calls the per-feature output "the hook for future 'learn from feedback'
iteration".

### 7e. How adaptation / import works

- **Import**: `voice_import` requires `name` (string) and `samples` (array of strings), optional
  `platform` (`src/voice.ts:33-45`). Empty/whitespace samples are filtered; if nothing remains it
  throws `'Provide at least one non-empty sample.'` (`src/voice.ts:54-58`). The fingerprint is
  extracted, the profile upserted, and the tool returns `{ id, sampleCount, fingerprint }` as a JSON
  value, rendered to text with `renderFingerprint` prefixed by
  `Imported voice profile "${v.id}" (${v.sampleCount} samples).` (`src/voice.ts:48-51`, `:73`).
- **Read / list**: `voice_profile` with no `name` returns `{ profiles: [...] }` where each entry is a
  projection of only `id, sampleCount, updatedAt, platforms, language, avgSentenceLength`
  (`src/voice.ts:92-101`); with a name it returns `{ profile }` (the **whole** `VoiceProfile`, including
  every `sampleExcerpt` verbatim) or throws `Voice profile "${args.name}" not found.` (`:103-105`).
- **Delete**: `voice_remove` requires `name`, returns `{ removed, id }` (`src/voice.ts:110-129`).
- **Adapt / rewrite**: `voice_rewrite` requires `text` + `name`; optional `strength`
  (`light|standard|aggressive`) and `language` (`auto|zh|en`) (`src/voice.ts:154-172`). It analyzes the
  draft, then calls `buildRewriteBrief({ report, strength, language, includeRules: false, fingerprint,
  excerpts: profile.sampleExcerpts })` and returns the resulting **string** (`src/voice.ts:181-189`).
  Note `includeRules: false` here versus `includeRules: true` in `humanize_rewrite`
  (`humanizer.ts:85`). There is **no automatic learning loop, no feedback capture, and no
  fingerprint drift/merge** — none found. Re-importing the same `name` **replaces** the profile
  wholesale (it does not blend with prior samples), and `sampleCount` becomes the count of the new
  call only (`src/voice.ts:63-72`).

### 7f. What is absent from the fingerprint

`none found` for: prosody/paragraph-level features, paragraph count or length, list/bullet usage,
heading usage, markdown/formatting habits, emoji, hedging *lexicon* distinct from the rule catalogue,
vocabulary richness beyond TTR, syntactic/dependency features, n-gram beyond bigrams, readability
indices, per-sample variance, register/formality score, language-mix ratio stored as a number,
traditional-Chinese support, or any embedding-based style vector. There is no schema version inside
`StyleFingerprint` itself — versioning lives only on the enclosing store file (§9).

## 8. Render / rewrite contract

`src/core/render.ts` produces **plain-text Markdown-ish instruction blocks addressed to the calling
agent (the LLM), not to a model API.** The module header states the contract explicitly
(`src/core/render.ts:2-4`): "Render analysis results and build rewrite briefs for the agent to apply.
The plugins never call the LLM themselves: they hand the agent a brief, and the agent performs the
rewrite in its own turn."

Three pure `format → string` functions plus the brief builder:

- `renderReport(report: HumanizeReport): string` (`render.ts:11-34`) — human-readable scan summary:
  header line `AI score: ${report.aiScore}/100 (higher = more AI-like)`, a `Language: … · sentences: …
  · words: …` line, an `Avg sentence length: … · burstiness: …` line, then patterns grouped by
  `RULE_CATEGORY_LABELS` as `- ${label}: ${count} hit(s) — "${phrase}" ×${count}; …`. If no issues:
  `'No AI patterns detected.'` and early return (`:16-19`).
- `renderRules(): string` (`render.ts:36-45`) — the full catalogue, one `## ${RULE_CATEGORY_LABELS[…]} —
  ${rule.id} (${rule.severity})` heading per rule, the `note`, then every pattern as a bullet. Header:
  `'AI-writing rules (severity 1 = mild, 3 = strong):'`.
- `renderFingerprint(fp: StyleFingerprint): string` (`render.ts:47-71`) — 4–6 lines: language/samples/
  words; sentence stats with `short`/`long` as percentages; punctuation per 100 tokens; stance;
  `Type-token ratio:`; optional `Top words:` / `Top openers:` (tokens only, **counts dropped**);
  optional `Platforms: k×v`.
- `buildRewriteBrief(opts: RewriteBriefOptions): string` (`render.ts:113-155`) — the actual contract
  payload.

`RewriteBriefOptions`, verbatim (`render.ts:73-82`):


The brief is assembled in this **fixed section order** (`render.ts:113-154`):

1. **Opening imperative**: `Rewrite the draft yourself, following the guidance below. Do not call
   another tool to rewrite.` (`:115`)
2. **Strength guidance**, one of exactly three verbatim strings from `STRENGTH_GUIDANCE`
   (`render.ts:84-88`):
   - `light`: "Make only minimal changes: remove the most obvious AI tells while preserving the
     original wording and structure."
   - `standard`: "Rewrite naturally: remove AI patterns, vary rhythm, and keep every fact and figure
     intact."
   - `aggressive`: "Rewrite freely: heavy de-AI edit. Restructure sentences, cut fluff, and keep only
     the substance and any facts, numbers, and citations."
3. **Language line**, only if `opts.language` set: `Write in ${opts.language}.` (`:118-120`)
4. **`## Hard rules`** (`:122-127`) — 5 verbatim bullets:
   - `- Preserve all facts, numbers, names, quotes, and citations exactly.`
   - `- Do not add new claims, examples, or data.`
   - `- Keep the original meaning and intended audience.`
   - `- Remove: empty openers, mechanical parallelism, summary endings, hedging filler, and template
     transitions.`
   - `- Vary sentence length; prefer concrete, specific wording over vague grand claims.`
5. **`## Issues detected in the draft`** (only if `opts.report`) — `AI score: ${aiScore}/100 ·
   ${issueCount} pattern hit(s).` then one bullet per issue as
   `- [${RULE_CATEGORY_LABELS[issue.category]}] "${issue.phrase}" ×${issue.count}` (`:130-137`)
6. **`## Target voice profile`** (only if `opts.fingerprint`), from `fingerprintSection`
   (`render.ts:90-102`): intro line `Rewrite to match these writing habits:` followed by 5 bullets —
   sentence length/rhythm/short/long, punctuation habits per 100 tokens, stance, `Preferred vocabulary:
   … || (none recorded)`, `Sentence openers often start with: … || (none recorded)`. Note it renders
   the **first-person rate, second-person rate, hedging, transitions, adverbs, contractions** but
   **omits** `hedgeRate`'s sibling `aiPhraseHits`, and renders no vocabulary counts.
7. **`## Representative samples (imitate style, never copy content)`** (only if `opts.excerpts`
   non-empty), from `excerptsSection` (`render.ts:104-111`), each as `Sample ${i + 1}:\n${e}`.
8. **`## Reference: AI patterns to avoid`** (only if `opts.includeRules`) — one bullet per rule as
   `- [${RULE_CATEGORY_LABELS[rule.category]}] ${rule.patterns.join(' | ')}`; the rule `id`, severity,
   and `note` are **not** included here, unlike `renderRules` (`:144-150`).
9. **`## Output`** — closing contract: `Output ONLY the rewritten text. No commentary, no preamble, no
   wrapping.` (`:152-153`)

**Who consumes it:** the agent itself, in its own turn. Two callers, both returning the brief as the
tool result so it lands in the agent's context: `humanize_rewrite` (`src/humanizer.ts:81-87`,
`includeRules: true`) and `voice_rewrite` (`src/voice.ts:182-189`, `includeRules: false`). Both declare
`output: { schema: { type: 'string' }, render: (_args, value) => [{ type: 'text', text: value }] }`.
**The functions are pure string builders — there is no JSON contract, no schema, no machine-readable
intermediate.** For a unified `HumanVoiceContract`, `buildRewriteBrief` is the natural donor but its
output is prose directives addressed to an LLM; it would need to be re-expressed as a structured object
(sections → fields) before it can serve as a cross-project contract. `RewriteBriefOptions` itself is the
closest existing structured shape and is worth adopting nearly as-is.

## 9. Store / persistence

- **Format**: JSON, pretty-printed with 2-space indent — `JSON.stringify(data, null, 2)`
  (`store.ts:62`).
- **Location**: constructor takes a `filePath`; `~` and `~/…` are expanded to `homedir()`
  (`store.ts:27-31`). Default is `'~/.dsh/voice-profiles.json'` (`src/index.ts:20`), i.e.
  `<user home>/.dsh/voice-profiles.json` — **outside any project workspace and outside the DSH storage
  subsystem.** The header explains why: "Deliberately decoupled from the harness storage subsystem so
  the plugin boots with no storage backend requirement." (`store.ts:3-4`). `mkdir(dirname(filePath),
  { recursive: true })` is called before every save (`store.ts:60`).
- **Schema / versioning**: `StoreFile.version` is the literal type `1`; `emptyStore()` writes
  `{ version: 1, profiles: {} }` (`store.ts:33-35`). On load, anything that fails the check
  `parsed && parsed.version === 1 && parsed.profiles` is **silently discarded and replaced by an empty
  store** (`store.ts:50`). There is **no migration path, no version bump handling, and no backup of a
  rejected file** — a future schema change silently destroys existing profiles. This is the single
  highest-risk behaviour in the module.
- **Read**: `load()` memoises into `this.cache` (`store.ts:39`, `:46`); an `ENOENT` is swallowed as an
  empty store (`:52-53`); **any other read error is rethrown** (`:52`). Because the cache is per-instance
  and `ProfileStore` is constructed once per `registerVoiceTools` call (`src/voice.ts:26`), a
  long-lived session never re-reads the file — external edits are invisible.
- **Write**: temp-file-then-rename for crash safety: write `${filePath}.tmp`, then `rename` over the
  target (`store.ts:61-63`). Not fsync'd, no file locking, so two concurrent DSH processes can lose
  writes.
- **Operations**: `list()` returns all profiles sorted by `updatedAt` **descending via string localeCompare**
  (`store.ts:66-69`) — ISO-8601 strings, so lexicographic order equals chronological order.
  `get(id)` is a plain map lookup returning `undefined` if absent (`:71-74`). `upsert(profile)` mutates
  the passed object's `updatedAt` in place, assigns by `profile.id`, saves, returns it (`:76-82`).
  `remove(id)` returns `false` if absent, otherwise deletes and saves (`:84-90`).
- **Not stored**: no index, no encryption, no redaction, no size limit on `sampleExcerpts` beyond the
  500-char × `maxExcerpts` cap applied at import time, and **no deletion of the `.tmp` file on failure**.

**Conclusion:** the two same-owner repos share **terminology and a handful of cliché headwords, but
zero rule ids, zero rule definitions, and zero copied code paths.** `humanize-text` has no rule
catalogue to merge; its contribution is the *methodology* layer (detector-in-the-loop, multi-engine,
translation chain) and a 30-entry AI-vocabulary substitution dict. Treat `humanize-text` as **kind D
(methodology, keep out of the default path)** plus a downloadable source of **~21 extra cliché headwords**
for `cliche-en`.

### 14c. Other upstreams

Only `stop-slop` and `Humanizer-zh` are named in-repo (`rules.ts:3`, `README.md:53`); both are
Markdown skills. The Chinese rule categories in `dsh-humanizer` map onto the same conceptual space as
the Chinese-localised skills (`humanizer-zh`, `humanizer-zh-cn`, `op7418/Humanizer-zh`), but the
patterns here (互联网黑话 like `赋能`/`抓手`/`闭环`/`颗粒度`, and 排比/总结式收尾 detection) are
expressed as regex over CJK with `.{0,N}` gap windows — a mechanism absent from Markdown skills
entirely. **No rule id, phrase list, or file is copied from any of them; the relationship is
conceptual.**

## 15. Integration recommendation

**Verdict: integrate `dsh-humanizer` as the primary structural donor for `human-voice-suite` — it is
the only upstream in the set that is executable TypeScript with a machine-readable rule schema, a
bilingual detector, and a real voice-profile model.** It supplies roughly the shape of the target
system; the siblings supply rule breadth and methodology.

Recommended order of work:

1. **Lift `src/core/` as the deterministic kernel** (`text.ts`, `rules.ts`, `analyze.ts`,
   `fingerprint.ts`, `score.ts`) — it is pure, dependency-free, and covered by 23 tests that can come
   along. Port it before touching any DSH registration code, and verify the port with the upstream
   tests unchanged. This immediately gives the new project bilingual sentence splitting, tokenizing,
   a 13-rule/175-pattern catalogue, a 25-field fingerprint, and a transparent similarity score.
2. **Adopt `StyleFingerprint` + `RewriteBriefOptions` as the seed of the unified voice interface and
   `HumanVoiceContract`.** `StyleFingerprint` already has 25 well-named leaf fields with per-100-token
   normalisation; `RewriteBriefOptions` (`{ report?, fingerprint?, excerpts?, strength, language?,
   includeRules? }`) is essentially a structured contract already. Do **not** adopt
   `buildRewriteBrief`'s prose string as the contract — keep it as one *renderer* of the structured
   contract, so the contract is machine-readable and other renderers (Chinese prompts, JSON output,
   compact prompts) become possible.
3. **Register a new DSH plugin rather than vendoring `src/index.ts` / `humanizer.ts` / `voice.ts`.**
   Re-implement the registration against the current DSH API, keep the tool *names* and *descriptions*
   as the compatibility surface, and drop the unsafe `as unknown as JsonValue` casts. Fix two things
   at the same time: make `output.schema` accurate for the JSON-returning tools, and move the
   `voice_profile` full-profile return (which leaks `sampleExcerpts`) to an explicit opt-in.

Mandatory fixes before the copied code is used on real user data:

- **`store.ts:50` — replace the silent `version !== 1 → empty store` fallback with a hard error or a
  real migration.** As written, any schema bump silently destroys every stored voice profile.
- **`rules.ts` overlapping literals (narrow, but fix anyway)** — `换句话说，` is claimed by both
  `over-explain-zh` (`:309`) and `transition-zh` (`:236`, as `^换句话说`); `值得注意的是` by both
  `hedge-zh` (`:203`) and `transition-zh` (`:236`, as `^值得注意的是，`). Verified to double-count only
  when the phrase opens the input. Fix by dropping the redundant `transition-zh` entries or by
  de-duplicating detections by matched span.
- **`analyze.ts:32-41` — the `aiScore` formula is saturating and unnormalised.** Max pre-clamp input is
  405; `severity × min(count,5) × 2` ignores text length entirely. Replace with a
  length-normalised density (the per-100-token habit already used in `fingerprint.ts:81-84`) so that
  scores are comparable across document sizes.
- **`rules.ts:319` — `^` anchors are compiled without the `m` flag**, so `^furthermore,` matches only
  at absolute string position 0. **Verified by execution:** `'a.\nFurthermore, b.'` does **not** match
  `^furthermore,` with flags `gi`, but does with `gim`. All **37** `^`-anchored patterns in
  `transition-en` (16), `transition-zh` (11), `summary-ending-en` (7), and `summary-ending-zh` (3:
  `^总之`, `^最后，`, `^让我们`) are therefore inert on everything except position 0 — i.e. **the
  transition and summary-ending categories are effectively dead on multi-paragraph input.** Add the
  `m` flag (and re-baseline `aiScore`, since scores will jump) or match sentence-by-sentence; the
  latter also fixes the double-count.

What to take from siblings instead of from this repo: the ~21 extra cliché headwords from
`humanize-text`'s `AI_VOCAB_REPLACEMENTS`; the 15 structural/formatting rules blader/humanizer covers
that `AI_RULES` cannot express; Chinese author-voice profiles from the Chinese skills. Keep
`humanize-text`'s multi-engine/translation-chain methodology **out of the default execution path**
(kind D).

## 16. Gaps, risks, and limitations

**Correctness and data-integrity risks**

1. **Silent data loss on schema mismatch** — `store.ts:50` discards the entire store file if
   `version !== 1`, with no error, no backup, and no rename of the bad file. Highest severity finding
   in the repo.
2. **The rule engine can double-count overlapping patterns** (`换句话说，`, `值得注意的是` — §4, §15).
   Verified to occur only when the phrase opens the input, so the practical impact is small, but the
   two rules are genuinely redundant and should be de-duplicated.
3. **`aiScore` is saturating and length-independent** — up to 405 raw points clamped to 100, no
   normalisation by token count (`analyze.ts:32-41`). A one-sentence tweet and a 5,000-word essay with
   the same raw hits score identically.
4. **`^`-anchored patterns are largely inert** — with flags `gi` and no `m` (`rules.ts:319`), `^`
   matches only position 0 of the whole input, so all **37** anchored patterns behave differently than
   their authors clearly intended (verified by execution: `gim` matches where `gi` does not). **This
   makes the entire `transition` category and most of `summary-ending` unreachable on real
   multi-paragraph input**, which silently depresses every `aiScore`. This is untested:
   `test/rules.test.ts` never exercises a `^` pattern in multi-paragraph text.
5. **Chinese first-person singular and plural are not distinguished** — `/我|我们|咱/g`
   (`fingerprint.ts:145`) resolves leftmost-first, so `我们` contributes a single hit and the `我们`
   alternative is unreachable; a writer who consistently uses 我们 is scored as if using 我.
6. **`topOpeners` is meaningless for unspaced Chinese** — `s.split(/\s+/)[0]` (`fingerprint.ts:110`)
   yields the entire sentence, so the "opener" for Chinese is the whole first sentence.
7. **CJK bigrams straddle punctuation and sentence boundaries** — the skeleton
   `(text.match(/[\u3400-\u9fff]+/g) ?? []).join('')` (`text.ts:86`) concatenates CJK runs without
   separators, producing spurious bigrams across sentence/paragraph breaks.
8. **No Chinese stopword list — none found** (`text.ts:93-99`), so Chinese `topWords` is dominated by
   function-word bigrams (`的是`, `我们`) and `typeTokenRatio` is not comparable between English and
   Chinese text.

**Coverage gaps**

9. **`groupIssues` is dead code** in `src/` — exported (`analyze.ts:61`) but called nowhere; and its
   `label` field returns the raw machine category rather than `RULE_CATEGORY_LABELS` (`analyze.ts:66-70`),
   inconsistent with `renderReport` (`render.ts:24`).
10. **`EMPTY_FINGERPRINT` is exported but unused** (`fingerprint.ts:214-223`) — no fallback path
    consumes it.
11. **10 of 25 fingerprint fields are never scored** (`secondPersonRate`, `transitionRate`,
    `aiPhraseHits`, `typeTokenRatio`, `topOpeners`, `medianLength`, `plus language`, `platforms`,
    `sampleCount`, `totalWords`) — `scoreSimilarity` ignores them (`score.ts:50-97`), so the reported
    similarity is blind to lexical richness and to how AI-ish the draft is. Notably a draft can score
    100 for voice-match while being full of AI clichés; the two scores are fully independent and never
    combined anywhere.
12. **No rule can express punctuation, formatting, or structural tells.** `#8 Dashes`, `#19 Bold as
    decoration`, `#20 Decorative headings`, `#21 Curly quotation marks`, `#11 Passive voice` from
    blader have no equivalent; `punctuation.emDash` is measured but never flagged.
13. **Simplified Chinese only** — every CJK pattern is Simplified (`rules.ts:76-88`, `:141-170`,
    etc.); traditional-Chinese input silently matches nothing.
14. **`mixed` language text is mislabelled as "English"** in rewrite briefs —
    `resolveLanguage` maps anything that is not exactly `'zh'` to `'English'` (`humanizer.ts:95`).

**Testing and quality gaps**

15. **`store.ts`, `render.ts`, `index.ts`, `humanizer.ts`, `voice.ts` have zero tests** — including
    all 8 tool registrations, all 4 render functions, and the store's version-reset path. That is
    roughly half the shipped modules.
16. **No lint step, no coverage measurement, no OS matrix** in CI (`.github/workflows/ci.yml:1-19`);
    CI is a single Ubuntu job on Node 22.
17. **No `engines` field** (`package.json`) — the project depends on `node --experimental-strip-types`
    (a Node ≥22.6 feature) for tests and on `@types/node ^24` for types, but declares no minimum Node,
    so nothing prevents installing it on an incompatible runtime.
18. **The committed `lib/` can drift from `src/`.** Nothing in CI verifies that the committed build
    output matches a fresh `tsc` run; `npm run check` builds but never diffs the result against git.

**Licensing / provenance risks**

19. **BSD-3-Clause obligations are real and non-zero** for a downstream MIT/Apache project: retain the
    copyright notice and disclaimer for source, reproduce both in documentation for binary
    redistribution (the committed `lib/` is binary-ish shipped output), and **do not imply
    lynote-ai endorsement** (§13).
20. **No `NOTICE`/`THIRD_PARTY`/`ACKNOWLEDGMENTS` file — none found**, even though `rules.ts:3` declares
    derivation from `stop-slop`, `blader/humanizer`, and `Humanizer-zh` (all MIT). The derivation is
    conceptual, so no MIT notice is strictly required, but the new project should record the lineage
    explicitly in its own notices file rather than reproducing this repo's silence.
21. **Holder-name inconsistency across the same owner** — the exact string in this repo's `LICENSE:3`
    is `Copyright (c) 2026, lynote-ai`, while the sibling `humanize-text` LICENSE says
    `Copyright (c) 2026 Lynote.ai` (different capitalisation, spacing, and punctuation). Attribute each
    repo from its own file; do not normalise them together.

**Unverified / out of scope**

22. No build, test, or install was executed, so the claims here are static-analysis claims only. In
    particular the **runtime behaviour of `detectIssues` on real corpora is unmeasured** — the false-positive
    rate of bare-word patterns such as `seamless`, `robust`, `somewhat`, `心智`, `红利` is unknown, and
    the illustrative scores in `examples/README.md` and `README.md:61-76` are **author statements, not
    measurements**.
23. The score tolerances and weights in `score.ts` are hand-tuned with no calibration dataset in the
    repo — `test/score.test.ts:23` only asserts self-similarity `>= 95`.
24. Commit `9314b95d0b` is the tip of `main` at clone time; upstream `main` may have moved since.
25. Nothing in this repo declares a version for the *fingerprint shape*; only the enclosing store file
    carries `version: 1` (`store.ts:23`), so a fingerprint format change is indistinguishable from a
    store format change.
