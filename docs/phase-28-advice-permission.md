# Phase 28: the advice-permission migration

<!-- The interface change `RULE_STATUS_DECISION.md` recorded as a design gap, closed. -->

`RULE_STATUS_DECISION.md` §1 ended with a refusal:

> **Interface design gap.** `requestKind` is a list of things the user asked for, and the rule tests
> membership. Absence therefore means *both* "the user did not ask" and "nobody knows whether the user
> asked" — the two states this design must keep apart. The gate needs a tri-state or an explicit unknown
> channel (for example `advicePermission: 'granted' | 'absent' | 'unknown'`). **Until that exists, the
> adapter is not implemented**, because any implementation would have to fold abstention into absence.

This phase implements exactly that interface and nothing else. No phrase was added to the rule, no
threshold moved, and A v1 was not touched.

## 1. What changed

| | Before | After |
| --- | --- | --- |
| The gate | `requestKind` membership | `advicePermission`, three states |
| Missing field | read as "the user asked for nothing" | `unknown` |
| `requestKind: []` | read as "the user asked for nothing" | `unknown` |
| A rule that could not tell | reported nothing | **abstains, and says so** |
| A rule the evidence ruled out | reported nothing | **reported as suppressed** |
| `behaviorScore` | — | **unchanged**, and the rule is still `shadow` |

New module: `src/behavior/permission/index.ts`.

```ts
export type AdvicePermission = 'granted' | 'absent' | 'unknown';
```

| State | Meaning | `chat.unsolicited_advice` |
| --- | --- | --- |
| `granted` | Evidence that the turn invited advice or a course of action | suppressed |
| `absent` | Positive evidence that the turn invited none | runs, and decides |
| `unknown` | Not enough evidence to decide | **abstains** |

`unknown` is the default. A missing field is not evidence, and neither is a list that happens not to
mention `advice`.

## 2. The adapter, and the frozen layer it reads

`HIGH → granted`, `LOW → absent`, `MEDIUM → unknown`, `UNCERTAIN → unknown`.

A v1 is read, not modified: `benchmarks/external/permission.ts` is byte-identical to what Phase 22
froze. Its four states map onto three, and the two that A v1 declines to decide (`MEDIUM`, `UNCERTAIN`)
become `unknown` rather than `absent`. Folding a judgement request into absence would rebuild the
original error from the other side.

The mapping is asserted against the real layer, not restated: `tests/behavior-advice-permission.test.ts`
imports `permissionOf` from `benchmarks/external/permission.ts` and runs every state through the adapter.

## 3. The legacy field

`ConversationContext.requestKind` is **kept**, and its semantics are narrowed:

- contains `advice` → `granted`;
- anything else, including `[]` and a missing field → **`unknown`**.

It can grant permission and it can do nothing else. That is the whole correction: a caller that supplied
a list of subjects analysed the turn, and a caller that supplied a list without `advice` in it did not
establish that the user asked for nothing.

The field is documented as legacy at its declaration, in the DSH tool schema, and here. New code passes
`advicePermission`.

## 4. Abstention is a third outcome, not a boolean

`measureSmells()` returns the smells it found, unchanged, so every existing caller keeps its shape. Beside
it:

- `measureSmellsDetailed()` returns `{ smells, abstained, suppressed }`;
- `BehaviorAssessment.abstained` and `.suppressed`, and the same two lists on `ScoreRationale`;
- `ScanResult.behaviorAbstained` and `.behaviorSuppressed`, so a caller does not have to read a rationale
  to find out that a rule declined to decide;
- the run file records them per sample, and `BENCHMARK_RESULTS.md` prints a section for them.

Nothing is folded into `false`. A rule that abstained, a rule that was suppressed and a rule that looked
and found nothing are three different records, and each prints differently:

```
No assistant smell found among 9 of 10 behaviours judgeable; chat.unsolicited_advice abstained on unknown advice permission.
```

`judgedCount` counts abstentions as unjudged, because that is what they are: nine of ten, not ten.

## 5. The measured effect

`benchmarks/external/ADVICE_PERMISSION.md` is the current measurement, generated by
`npm run advice:permission`. Its first section is a reproduction check: with the permission forced to
`absent` on every turn — the pre-Phase-B behaviour — the per-arm firing counts on the 2,000-item paired
baseline come back as `0 / 32 / 14 / 22`, digit for digit what `PAIRED_CONTROL.md` published. **The only
thing that changed between the published numbers and the new ones is the gate.**

With the gate live, on the same 2,000 items:

| Arm | `absent` + fired | `absent` + quiet | `granted` + suppressed | `unknown` + abstained |
| --- | --- | --- | --- | --- |
| `human` | 0 | 450 | 0 | 1550 |
| `plain` | 8 | 442 | 0 | 1550 |
| `default` | 4 | 446 | 0 | 1550 |
| `post` | 3 | 447 | 0 | 1550 |

Two facts about that table matter more than the firings, and both are in the report:

1. **A v1 granted permission 0 times in 2,000 turns, and read 0 as `MEDIUM`.** LCCC is casual Weibo
   chatter: people share and vent rather than ask for methods. So on this baseline the suppression path
   is never taken, and the `granted` and `MEDIUM` branches are exercised by the integration regression and
   by the two `granted` samples in the committed corpus rather than by these turns.
2. **It abstained on 77.5%.** The claim that may be made is therefore not "the gate made the rule more
   precise". It is: the gate made the rule's silence legible. Where a rate is quoted, its denominator is
   the 450 decided turns, not 2,000.

On the committed corpus the advice rule falls from 7 firings to 4 in `BENCHMARK_RESULTS.md`, and the
abstentions appear in a new section of that report. `behaviorScore` does not move: the rule is `shadow`
and charges nothing, which the integration test asserts for all four permission states.

## 6. The corpus records the evidence

A permission is a property of the user turn, and only the caller has the turn. So the committed corpus
records it: `advice_permission: granted | absent | unknown` in the front matter, annotated from A v1 by
`npm run advice:annotate` and verified by `npm run advice:annotate -- --check`.

32 of 71 samples carry a user turn; 2 read `granted`, 12 `absent`, 18 `unknown`. The 18 are all English,
because A v1's signals are Chinese constructions — an undecidable-by-construction result, recorded rather
than worked around. The field is covered by the corpus hash, because a run whose recorded permission
changed is a different run.

A sample may not record a permission without a user turn, and a value outside the three states throws at
load time: an unrecognised value would silently become `unknown`, which is a different claim.

## 7. Historical numbers

Nothing was regenerated to make the past look like the present.

- `PAIRED_CONTROL.md`, `LENGTH_MATCHED.md`, `HELPSTEER3_EVALUATION.md`, `LEXICAL_ONLY_CLASSIFICATION.md`
  and `COVERAGE_MATRIX.md` keep the numbers they were published with, and every advice rate in them is
  quoted with the qualifier **"measured with `requestKind` unpopulated"**.
- The tools that produced those reports are unchanged, so a re-run of one of them now abstains on that
  rule instead of firing it. That is recorded here so nobody reads a stale report as a live one:
  **the historical tools are historical.**
- `BENCHMARK_RESULTS.md` and `ADVICE_PERMISSION.md` are the current reports, and both use the new
  semantics.

## 8. What this does not do

- It does not promote the rule. `chat.unsolicited_advice` stays `shadow`; plumbing is not validation.
- It does not widen the phrase list. Five phrases, unchanged.
- It does not validate the rule under its new behaviour. Its operational meaning changed when the gate
  went live, so the old data cannot speak for the new behaviour and a promotion would need its own blind
  review.
- It does not give the rule a precision figure under `absent`. The nineteen "legitimate advice after
  permission" replies in the lexical-only cell say the phrase list is not the whole story, and the gate
  addresses the permission half only.
- It does not extend the tri-state to `chat.unrequested_background`, which has the same structural defect:
  its `unrequested` qualifier is read from `requestKind`, that gate is still never populated, and the rule
  is class A, so changing it would move `behaviorScore`. That is a real finding, recorded as a limitation
  rather than fixed in a phase whose whole point was that the score must not drift.
